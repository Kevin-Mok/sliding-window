## **Difficulty Rationale**

The optimized order keeps the original problem scope but makes the cognitive jump smaller: scalar fixed window → scalar variable window → map-based variable window → coverage-map homework. The key change is moving `variable-demo` before `shortest-study-sprint`, because students need to see repeated shrinking before they code it. This follows the worked-example-before-independent-practice pattern: MIT’s Teaching + Learning Lab describes worked examples as step-by-step illustrations that help novices focus on principles before solving independently, especially when new concepts and procedures would otherwise overload them. ([Teaching + Learning Lab][1])

**Why this order works now:**

1. **`best-k-day-step-streak` stays first.**
   It has one fixed length, one scalar state, one add, one remove, and one best update. This is the cleanest entry point.

2. **`fixed-proof` comes immediately after Problem 1.**
   Students have just written the fixed-window loop, so the `O(n)` proof is concrete: each index enters once and exits once.

3. **`pattern-decision` stays before variable problems.**
   It gives students the rule they will reuse: ask whether `left` can move more than once.

4. **`variable-demo` moves before `shortest-study-sprint`.**
   This is the most important flow improvement. The baseline taught repeated shrinking after the first variable-size problem; the revision teaches the trace first, then asks students to code it.

5. **`shortest-study-sprint` comes before count maps.**
   It introduces repeated shrinking with only one scalar state: `current_sum`.

6. **`invariant` comes before `longest-club-code-with-limited-symbols`.**
   Counts are harder than sums because a stale count can silently corrupt validity. The invariant slide gives students a short debug sentence before the map problem.

7. **`longest-club-code-with-limited-symbols` remains the hardest in-class problem.**
   It adds a frequency map, duplicate handling, zero deletion, and validity timing. It is still manageable after students already know expand → shrink → update.

8. **`smallest-announcement-clip` remains homework.**
   It is not just “another map problem.” It adds coverage bookkeeping with `needed/have`, minimum-window timing, and required-character logic. That is a larger jump, so it should stay outside class unless pacing is unusually fast.

The student checks are intentionally short, frequent, and low-stakes. That matches check-for-understanding guidance that CFUs should happen directly after concepts, provide observable evidence, and be acted on immediately. ([College of LSA][2]) The lesson also fades support: students begin with classification and guided trace, then move to implementation, then debug using invariants, which fits CS scaffolding guidance that support can be gradually reduced as tasks become more open. ([Teach Computing][3])

## **Risk & Recovery Matrix**

| Risk                                                      | Signal                                                                         | Fix script                                                                                                                         |
| --------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Students classify by values instead of wording.           | They start tracing before naming fixed/variable.                               | “Freeze the values. Circle the clue word. Exact `k` means fixed; threshold or coverage means variable.”                            |
| Students store the whole window instead of minimal state. | They build lists of subarrays.                                                 | “What changes after one slide? Only one value enters and one value exits. Keep only what lets you update that.”                    |
| Problem 1 off-by-one removal.                             | They subtract `steps[right]`, `steps[left]` incorrectly, or start loop at `0`. | “At `right = 4`, point to the entering value. Now count back `k` spots. That value exits.”                                         |
| Students think fixed window is `O(n*k)`.                  | They describe summing every window from scratch.                               | “That would be the brute force. Our code does not rescan. Each index enters once and exits once.”                                  |
| Students use `if` instead of `while` in Problem 2.        | Their sample returns too large or misses length `2`.                           | “Replay `right = 3`. After one shrink, is the window still valid? Yes. That means one `if` is not enough.”                         |
| Students update best after shrinking in Problem 2.        | They miss the valid window before it becomes invalid.                          | “Best is recorded while the window is legal. Shrinking may destroy legality, so record first, then remove.”                        |
| Students mishandle impossible case in Problem 2.          | They return `len(blocks)` or a sentinel.                                       | “The sentinel is not an answer. If it never changed, no sprint worked; return `0`.”                                                |
| State invariant drifts.                                   | Their `current_sum` or `counts` no longer matches `[left:right+1]`.            | “Stop coding. Read the invariant out loud. Now compare state to the actual window. Fix the first row where they differ.”           |
| Students use a set for Problem 3.                         | Duplicate-heavy sample fails.                                                  | “In `AAH`, remove one `A`. Does `A` disappear? No. A set cannot know that; counts can.”                                            |
| Students forget to delete zero-count keys.                | `len(counts)` stays too large.                                                 | “A zero count means the character is outside the window. Delete the key so distinct count matches the window.”                     |
| Students update best while Problem 3 window is invalid.   | They count substrings with more than `k` distinct symbols.                     | “Validity first, best second. Shrink until `len(counts) <= k`, then update best.”                                                  |
| Class runs behind after Problem 2.                        | Less than 30 minutes remain for invariant + Problem 3.                         | “Switch to rescue mode: one invariant sentence, one duplicate trace, then guided skeleton for Problem 3. Homework stays homework.” |

## **Top 10 Slide Talking Points**

1. “Do not trace first. Classify first.”
2. “Exact `k` means fixed window.”
3. “Threshold or coverage means variable window.”
4. “State is what survives from one row to the next.”
5. “Right adds; left removes.”
6. “Fixed window: one item enters, one item exits.”
7. “Variable window: one right move can cause many left moves.”
8. “Use `while` when left may move more than once.”
9. “Best updates only when the current window is valid.”
10. “The invariant is your debugger: state must match `[left:right+1]`.”
